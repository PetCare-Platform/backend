# 쿠폰 발급 동시성 실험 결과

## 1. 개요

본 문서는 각 쿠폰 발급 동시성 제어 전략의 실제 측정 결과를 기록한다.

실험 설계 및 조건은 다음 문서를 기준으로 한다.

- [동시성 실험 설계](./concurrency-experiment.md)
- [공통 코드 구조](./common-code.md)

> [!IMPORTANT]
> 측정하지 않은 값은 예상값으로 채우지 않고 `-`로 기록한다.

### 문서 구성 원칙

| 영역 | 정렬 축 | 작성 시점 |
|---|---|---|
| 측정 기록 (5~7장) | 단계 축 — 한 단계에서 전 전략을 한 표에 비교 | 각 단계 실행 직후 |
| 해석·분석 (8~11장) | 전략 축 — 전략별 특성과 장단점 | 전체 측정 완료 후 |

같은 조건에서 전략을 나란히 비교하는 것이 이 실험의 목적이므로 측정값은 단계 축으로 기록한다.

### 2.2 서버 설정 기록

설계 문서 §16이 결과 해석에 필요하다고 명시한 항목이다. 실험 도중 아래 값을 변경하면 변경 전후 결과를 같은 표에 넣을 수 없다.

| 항목 | 값 |
|---|---|
| Tomcat thread / accept queue | 기본값 (max-threads 200) — 별도 설정하지 않음 |
| HikariCP pool size | **기본값 10** — 별도 설정하지 않음 |
| JPA isolation level | 기본값 (MySQL InnoDB REPEATABLE READ). 단 `OPTIMISTIC`은 구현에서 `READ_COMMITTED` 지정 |
| JVM 옵션 | 기본값 — `java -jar app.jar` 로 실행 |
| MySQL 주요 설정 | `mysql:8.0` 이미지 기본값 |
| Redis 설정 | `--appendonly no` |
| Kafka 파티션 수 | 3 |
| Kafka Consumer 동시성 | 3 |
| Consumer 재시도 정책 | 1초 간격 2회 (최초 포함 총 3회) |

> `application.properties`에 커넥션 풀·스레드 관련 설정이 하나도 없으므로 위 값은 모두 프레임워크 기본값이다. 특히 **HikariCP 기본 풀 크기 10**은 결과 해석에 직접 영향을 준다. 5.5의 DB 전략 처리량 수렴을 이 값과 함께 읽어야 한다.

```http
POST /experiment/coupons
{ "quantity": 100 }
```

## 4. 실행 규칙

### 4.1 RUN_ID 명명

```
{환경}-{단계}-{회차}
```

| 단계 | RUN_ID 예시 | 결과 파일 예시 |
|---|---|---|
| 스모크 | `aws-smoke-1` | `load-test/results/direct-aws-smoke-1.json` |
| 기본 | `aws-basic-1` ~ `-3` | `load-test/results/pessimistic-aws-basic-2.json` |
| 중간 | `aws-mid-1` ~ `-3` | `load-test/results/redis-aws-mid-3.json` |
| 공통최대 | `aws-max-1` ~ `-3` | `load-test/results/conditional-aws-max-1.json` |
| 최종 | `aws-final-1` ~ `-3` | `load-test/results/kafka-aws-final-1.json` |

결과 파일명은 k6가 `{전략}-{RUN_ID}.json` 형식으로 자동 생성한다. 실행 시 `RUN_ID`만 지정하면 된다.

### 4.2 반복 횟수

| 단계 | 반복 | 사유 |
|---|---:|---|
| 스모크 | 1회 | 환경과 스크립트 동작 확인용이며 비교 대상이 아니다 |
| 기본 / 중간 / 공통최대 | 3회 | 설계 문서 §13의 최소 반복 기준 |
| 최종 검증 | 3회 | 동일 |

**워밍업 분리 여부: 분리하지 않는다.**

설계 문서 §13이 최종 실험 전 확정하도록 유보한 항목이며, 실험 A 결과를 근거로 다음과 같이 결정했다.

| 단계 | 1회차 → 3회차 (`CONDITIONAL` req/s) | 변화 |
|---|---|---:|
| 기본 | 166.21 → 188.87 | +13.6% |
| 중간 | 225.28 → 224.48 | -0.4% |
| 공통최대 | 236.10 → 233.62 | -1.1% |

워밍업 영향은 요청 수가 적은 기본 단계에서만 뚜렷하고, 중간·공통최대에서는 사라진다. 기본 단계의 편차도 3회 평균으로 흡수되므로 최초 실행을 별도로 제외하지 않는다. 대신 회차별 개별값을 모두 기록해 편차를 확인할 수 있게 한다.

### 4.3 KAFKA 전용 실행 옵션

`KAFKA` 전략은 teardown에서 Consumer의 DB 저장 완료까지 폴링한다. 단계가 커지면 대기 상한을 함께 올린다. 값을 올리지 않으면 Kafka가 정상인데도 정합성 검증이 실패로 기록된다.

| 단계 | `KAFKA_WAIT_TIMEOUT` | `MAX_DURATION` |
|---|---:|---|
| 스모크 | 30 (기본값) | 2m (기본값) |
| 기본 | 60 | 2m |
| 중간 | 180 | 5m |
| 공통최대 | 300 | 5m |
| 최종 | 900 | 10m |

`teardownTimeout`은 `KAFKA_WAIT_TIMEOUT + 60초`로 자동 계산되므로 별도로 지정하지 않는다.

- 부하 요청 처리 중 Reset API 호출
- 실험 도중 2.2의 서버 설정 변경

## 5. 실험 A — 재고 차감 전략 비교

`DIRECT`, `PESSIMISTIC`, `OPTIMISTIC`, `CONDITIONAL`, `REDIS`의 재고 차감 성능과 정합성을 비교한다.

> [!NOTE]
> **잔여재고 열의 기준이 전략마다 다르다.**
> `DIRECT`·`PESSIMISTIC`·`OPTIMISTIC`·`CONDITIONAL`은 `dbRemainingQuantity`,
> `REDIS`는 `redisRemainingQuantity`를 기록한다. (설계 문서 §9.2)
>
> **`DIRECT`의 정합성 열은 O/X 판정이 아니라 `관찰`이다.**
> 동시성 제어가 없는 기준 전략이므로 정합성 통과를 강제하지 않고, 발생한 불일치 자체를 결과로 기록한다.

- `REDIS`는 처리량 545 req/s로 DB 전략 최고치(`CONDITIONAL` 178)의 **3.1배**다.

## 6. 실험 B — 처리 파이프라인 비교

Redis 재고 선점 로직은 동일하게 유지하고, DB 발급 이력 저장을 **동기 호출(`REDIS`)** 로 처리하는지 **Kafka Consumer가 비동기(`KAFKA`)** 로 처리하는지만 비교한다.

> [!NOTE]
> 두 전략은 완료 기준이 다르다. `REDIS`는 HTTP 응답 시점에 DB 저장이 끝나지만, `KAFKA`는 `WAITING` 응답 후 Consumer 처리가 끝나야 완료다. 따라서 **API 접수 지연시간**과 **최종 DB 저장 완료시간**을 분리해 읽어야 한다.

> `REDIS` 행은 실험 A와 동일 조건·동일 세션에서 측정한 값을 재사용할 수 있다. 재사용한 경우 비고에 명시한다.

| 2,000 VU 실행 중 최대 사용량 | 949 MB |
| 2,000 VU에 k6가 사용한 메모리 | 329 MB |
| VU당 메모리 사용량 (계산값) | 약 0.165 MB |
| 20,000 VU 예상 필요 메모리 | 약 3.3 GB (+ 유휴 620 MB) |
| 선택한 인스턴스 타입 | 실험 B 이후 결정 |
| 분산 실행 여부 | 실험 B 이후 결정 |

> **이 계산값은 보수적으로 다뤄야 한다.** k6 공식 문서는 VU당 1~5 MB를 안내하는데 측정값은 0.165 MB로 10배 이상 낮다. 스크립트가 요청 하나에 카운터 몇 개뿐이라 낮게 나올 수 있으나, 2초 간격 샘플링이 순간 피크를 놓쳤을 가능성도 있다. 공식 수치를 적용하면 20,000 VU에 20 GB가 필요해 현재 인스턴스로는 부족하다.
>
> **메모리보다 먼저 걸리는 제약이 있다.** 부하 발생기의 `ulimit -n`이 기본 1,024이므로 20,000개 동시 연결에 필요한 파일 디스크립터가 부족하다. 실행 직전 같은 셸에서 `ulimit -n 100000`을 반드시 적용한다. 커널 파라미터(`ip_local_port_range`)는 재부팅 시 초기화되므로 함께 재적용한다.
