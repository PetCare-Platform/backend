# 쿠폰 발급 동시성 실험 결과

## 1. 개요

본 문서는 각 쿠폰 발급 동시성 제어 전략의 실제 측정 결과를 기록한다.

실험 설계 및 조건은 다음 문서를 기준으로 한다.

- [동시성 실험 설계](./concurrency-experiment.md)
- [공통 코드 구조](./common-code.md)

> [!IMPORTANT]
> 측정하지 않은 값은 예상값으로 채우지 않고 `-`로 기록한다.

### 문서 구성 원칙

| 영역 | 정렬 축 | 작성 시점 |
|---|---|---|
| 측정 기록 (5~7장) | 단계 축 — 한 단계에서 전 전략을 한 표에 비교 | 각 단계 실행 직후 |
| 해석·분석 (8~11장) | 전략 축 — 전략별 특성과 장단점 | 전체 측정 완료 후 |

같은 조건에서 전략을 나란히 비교하는 것이 이 실험의 목적이므로 측정값은 단계 축으로 기록한다.

## 4. 실행 규칙

### 4.1 RUN_ID 명명

```
{환경}-{단계}-{회차}
```

| 단계 | RUN_ID 예시 | 결과 파일 예시 |
|---|---|---|
| 스모크 | `aws-smoke-1` | `load-test/results/direct-aws-smoke-1.json` |
| 기본 | `aws-basic-1` ~ `-3` | `load-test/results/pessimistic-aws-basic-2.json` |
| 중간 | `aws-mid-1` ~ `-3` | `load-test/results/redis-aws-mid-3.json` |
| 공통최대 | `aws-max-1` ~ `-3` | `load-test/results/conditional-aws-max-1.json` |
| 최종 | `aws-final-1` ~ `-3` | `load-test/results/kafka-aws-final-1.json` |

결과 파일명은 k6가 `{전략}-{RUN_ID}.json` 형식으로 자동 생성한다. 실행 시 `RUN_ID`만 지정하면 된다.

### 4.2 반복 횟수

| 단계 | 반복 | 사유 |
|---|---:|---|
| 스모크 | 1회 | 환경과 스크립트 동작 확인용이며 비교 대상이 아니다 |
| 기본 / 중간 / 공통최대 | 3회 | 설계 문서 §13의 최소 반복 기준 |
| 최종 검증 | 3회 | 동일 |

### 4.3 KAFKA 전용 실행 옵션

`KAFKA` 전략은 teardown에서 Consumer의 DB 저장 완료까지 폴링한다. 단계가 커지면 대기 상한을 함께 올린다. 값을 올리지 않으면 Kafka가 정상인데도 정합성 검증이 실패로 기록된다.

| 단계 | `KAFKA_WAIT_TIMEOUT` | `MAX_DURATION` |
|---|---:|---|
| 스모크 | 30 (기본값) | 2m (기본값) |
| 기본 | 60 | 2m |
| 중간 | 180 | 5m |
| 공통최대 | 300 | 5m |
| 최종 | 900 | 10m |

`teardownTimeout`은 `KAFKA_WAIT_TIMEOUT + 60초`로 자동 계산되므로 별도로 지정하지 않는다.

### 4.4 실행 중 금지 사항

- 부하 요청 처리 중 Reset API 호출
- 실험 도중 2.2의 서버 설정 변경
- 하나의 쿠폰에 서로 다른 전략 호출
- 부하테스트용 서버에서 `./gradlew test` 실행 (테스트 코드의 `flushDb()`가 Redis 전체를 삭제한다)

## 5. 실험 A — 재고 차감 전략 비교

> [!NOTE]
> **잔여재고 열의 기준이 전략마다 다르다.**
> `DIRECT`·`PESSIMISTIC`·`OPTIMISTIC`·`CONDITIONAL`은 `dbRemainingQuantity`,
> `REDIS`는 `redisRemainingQuantity`를 기록한다. (설계 문서 §9.2)
>
> **`DIRECT`의 정합성 열은 O/X 판정이 아니라 `관찰`이다.**
> 동시성 제어가 없는 기준 전략이므로 정합성 통과를 강제하지 않고, 발생한 불일치 자체를 결과로 기록한다.

## 6. 실험 B — 처리 파이프라인 비교

Redis 재고 선점 로직은 동일하게 유지하고, DB 발급 이력 저장을 **동기 호출(`REDIS`)** 로 처리하는지 **Kafka Consumer가 비동기(`KAFKA`)** 로 처리하는지만 비교한다.

> [!NOTE]
> 두 전략은 완료 기준이 다르다. `REDIS`는 HTTP 응답 시점에 DB 저장이 끝나지만, `KAFKA`는 `WAITING` 응답 후 Consumer 처리가 끝나야 완료다. 따라서 **API 접수 지연시간**과 **최종 DB 저장 완료시간**을 분리해 읽어야 한다.
>
> `REDIS` 행은 실험 A와 동일 조건·동일 세션에서 측정한 값을 재사용할 수 있다. 재사용한 경우 비고에 명시한다.
