# 쿠폰 발급 동시성 실험 결과

## 1. 개요

본 문서는 각 쿠폰 발급 동시성 제어 전략의 실제 측정 결과를 기록한다.

실험 설계 및 조건은 다음 문서를 기준으로 한다.

- [동시성 실험 설계](./concurrency-experiment.md)
- [공통 코드 구조](./common-code.md)

> [!IMPORTANT]
> 측정하지 않은 값은 예상값으로 채우지 않고 `-`로 기록한다.

### 문서 구성 원칙

| 영역 | 정렬 축 | 작성 시점 |
|---|---|---|
| 측정 기록 (5~8장) | 단계 축 — 한 단계에서 전 전략을 한 표에 비교 | 각 단계 실행 직후 |
| 해석·분석 (9~12장) | 전략 축 — 전략별 특성과 장단점 | 전체 측정 완료 후 |

같은 조건에서 전략을 나란히 비교하는 것이 이 실험의 목적이므로 측정값은 단계 축으로 기록한다.

## 3. 쿠폰 매핑표

전략별로 쿠폰을 분리하고, 재고 규모가 바뀌면 쿠폰을 새로 생성한다. Reset API는 재고를 기존 `total_quantity`로 되돌릴 뿐 총재고 수량을 바꾸지 못하므로 단계마다 새 쿠폰이 필요하다.

```http
POST /experiment/coupons
{ "quantity": 100 }
```

## 4. 실행 규칙

### 4.1 RUN_ID 명명

```
{환경}-{단계}-{회차}
```

| 단계 | RUN_ID 예시 | 결과 파일 예시 |
|---|---|---|
| 스모크 | `aws-smoke-1` | `load-test/results/direct-aws-smoke-1.json` |
| 기본 | `aws-basic-1` ~ `-3` | `load-test/results/pessimistic-aws-basic-2.json` |
| 중간 | `aws-mid-1` ~ `-3` | `load-test/results/redis-aws-mid-3.json` |
| 공통최대 | `aws-max-1` ~ `-3` | `load-test/results/conditional-aws-max-1.json` |
| 최종 | `aws-final-1` ~ `-3` | `load-test/results/kafka-aws-final-1.json` |

결과 파일명은 k6가 `{전략}-{RUN_ID}.json` 형식으로 자동 생성한다. 실행 시 `RUN_ID`만 지정하면 된다.

### 4.2 반복 횟수

| 단계 | 반복 | 사유 |
|---|---:|---|
| 스모크 | 1회 | 환경과 스크립트 동작 확인용이며 비교 대상이 아니다 |
| 기본 / 중간 / 공통최대 | 3회 | 설계 문서 §13의 최소 반복 기준 |
| 최종 검증 | 3회 | 동일 |

**워밍업 분리 여부: 분리하지 않는다.**

설계 문서 §13이 최종 실험 전 확정하도록 유보한 항목이며, 실험 A 결과를 근거로 다음과 같이 결정했다.

| 단계 | 1회차 → 3회차 (`CONDITIONAL` req/s) | 변화 |
|---|---|---:|
| 기본 | 166.21 → 188.87 | +13.6% |
| 중간 | 225.28 → 224.48 | -0.4% |
| 공통최대 | 236.10 → 233.62 | -1.1% |

워밍업 영향은 요청 수가 적은 기본 단계에서만 뚜렷하고, 중간·공통최대에서는 사라진다. 기본 단계의 편차도 3회 평균으로 흡수되므로 최초 실행을 별도로 제외하지 않는다. 대신 회차별 개별값을 모두 기록해 편차를 확인할 수 있게 한다.

### 4.3 KAFKA 전용 실행 옵션

`KAFKA` 전략은 teardown에서 Consumer의 DB 저장 완료까지 폴링한다. 단계가 커지면 대기 상한을 함께 올린다. 값을 올리지 않으면 Kafka가 정상인데도 정합성 검증이 실패로 기록된다.

| 단계 | `KAFKA_WAIT_TIMEOUT` | `MAX_DURATION` |
|---|---:|---|
| 스모크 | 30 (기본값) | 2m (기본값) |
| 기본 | 60 | 2m |
| 중간 | 180 | 5m |
| 공통최대 | 300 | 5m |
| 최종 | 900 | 10m |

`teardownTimeout`은 `KAFKA_WAIT_TIMEOUT + 60초`로 자동 계산되므로 별도로 지정하지 않는다.

## 5. 실험 A — 재고 차감 전략 비교

`DIRECT`, `PESSIMISTIC`, `OPTIMISTIC`, `CONDITIONAL`, `REDIS`의 재고 차감 성능과 정합성을 비교한다.

> [!NOTE]
> **잔여재고 열의 기준이 전략마다 다르다.**
> `DIRECT`·`PESSIMISTIC`·`OPTIMISTIC`·`CONDITIONAL`은 `dbRemainingQuantity`,
> `REDIS`는 `redisRemainingQuantity`를 기록한다. (설계 문서 §9.2)
>
> **`DIRECT`의 정합성 열은 O/X 판정이 아니라 `관찰`이다.**
> 동시성 제어가 없는 기준 전략이므로 정합성 통과를 강제하지 않고, 발생한 불일치 자체를 결과로 기록한다.

## 6. 실험 B — 처리 파이프라인 비교

Redis 재고 선점 로직은 동일하게 유지하고, DB 발급 이력 저장을 **동기 호출(`REDIS`)** 로 처리하는지 **Kafka Consumer가 비동기(`KAFKA`)** 로 처리하는지만 비교한다.

> [!NOTE]
> 두 전략은 완료 기준이 다르다. `REDIS`는 HTTP 응답 시점에 DB 저장이 끝나지만, `KAFKA`는 `WAITING` 응답 후 Consumer 처리가 끝나야 완료다. 따라서 **API 접수 지연시간**과 **최종 DB 저장 완료시간**을 분리해 읽어야 한다.
>
> **`REDIS`는 실험 A 결과를 재사용하지 않고 실험 B에서 다시 측정했다.** 재측정에 2분밖에 걸리지 않는 반면, 실험 A의 `REDIS`는 세션 초반에 측정되어 `KAFKA`와 JVM 워밍업 상태가 달라진다. 두 전략을 나란히 비교하는 것이 실험 B의 목적이므로 측정 시점을 맞췄다.

> [!WARNING]
> **`req/s` 열로 두 전략을 비교하면 안 된다.**
>
> k6는 `req/s`를 `요청 수 ÷ 전체 실행 시간`으로 계산하는데, `KAFKA`는 teardown에서 Consumer의 DB 저장 완료를 기다린 시간이 분모에 포함된다. 그 결과 요청 자체는 훨씬 빠른데도 `req/s`가 낮게 표시된다.
>
> 공통최대 1회차 기준: `KAFKA`는 요청당 241ms로 `REDIS`(1,294ms)보다 5.4배 빠르지만, 전체 실행 시간이 4.68초(`REDIS` 2.30초)라 `req/s`는 428 대 871로 역전되어 나타난다.
>
> 두 전략의 비교는 **6.5의 API 접수 지연시간 표와 최종 완료시간 표**를 기준으로 한다.

## 7. 중복·멱등성 검증

설계 문서 §7의 두 시나리오를 6개 전략 전체에 대해 실행했다. 성능 비교와 분리해 실행하는 것이 설계 문서의 요구사항이다.

> [!NOTE]
> **실행 순서가 설계 문서 §17과 다르다.**
> §17은 이 검증을 5번(실험 A 직후)에 두었으나 실제로는 실험 A·B를 마친 뒤에 실행했다.
> 재고 차감 경로와 중복 검사 경로가 독립적이고, 이 검증은 성능 측정이 아니라 동작 확인이므로
> 실행 시점이 결과에 영향을 주지 않는다. `KAFKA`까지 6개 전략을 한 번에 비교할 수 있어
> 결과표가 더 명확해지는 이점도 있다.

### 7.1 검증 범위

| 시나리오 | 보내는 요청 | 검증 대상 | 방어 장치 |
|---|---|---|---|
| ① `same-user` | 같은 `userId`, **다른** `requestId`로 10회 동시 | 1인 1매 규칙 | `UNIQUE (coupon_id, user_id)` / Redis 사용자 키 |
| ② `same-request` | 같은 `userId`, **같은** `requestId`로 10회 동시 | 멱등성 | `UNIQUE (request_id)` / Redis requestId 키 |

②가 엄밀한 의미의 멱등성이고, ①은 비즈니스 규칙이 동시 요청에서도 지켜지는지 본다. 두 시나리오는 **서로 다른 방어 장치**를 검증하므로 하나가 통과해도 다른 하나를 보장하지 않는다.

> [!IMPORTANT]
> **완전한 응답 멱등성은 이번 범위가 아니다.** 설계 문서 §7이 명시한 대로 현재 구현은 동일 `requestId` 재전송 시 최초 응답을 재반환하지 않고 409 `DUPLICATE_REQUEST`로 차단한다. 여기서는 **동일 요청이 재고와 발급 이력에 두 번 이상 반영되지 않는지**만 검증한다. 최초 처리 결과를 재반환하는 완전한 멱등성은 최종 시스템 구현 후 별도 과제다.

**실행 조건**

| 항목 | 값 |

| 동시 요청 수 | 10 (설계 문서 §7 규격) |

### 7.5 관찰 내용

- **`DIRECT`도 중복은 막았다.** 재고 차감에서는 약 90%의 갱신 유실을 보였던 전략이 중복 차단은 36회 전부 통과했다. DB의 `UNIQUE (coupon_id, user_id)`와 `UNIQUE (request_id)` 제약이 최종 방어선으로 작동한 것이 실증됐다. 설계 문서가 제약을 최종 방어선으로 둔 판단이 유효했음을 보여준다.

- **DB 전략 4개는 시나리오 ②에서도 `DUPLICATE_USER`로 응답했다.** 같은 사용자이기도 하므로 사용자 검사에 먼저 걸린 것이다. `REDIS`·`KAFKA`만 `DUPLICATE_REQUEST`로 정확히 구분했다. 기능상 문제는 아니지만, 사용자에게 "이미 발급받으셨습니다"와 "이미 처리된 요청입니다"는 다른 안내이므로 오류 코드의 정확도에서 차이가 있다.

- **`REDIS`와 `KAFKA`는 중복 차단 성능에 유의미한 차이가 없다.** `KAFKA` 전략도 재고 선점에 `RedisCouponStockService`의 동일한 Lua Script를 사용하므로 차단 경로가 완전히 같다. 측정된 0.8ms 차이는 10건 중 성공한 1건에서 `REDIS`가 DB 저장을 동기로 기다리는 데서 발생한 것이며, 실험 B에서 측정한 접수 지연시간 차이가 축소되어 나타난 값이다. **이 검증은 두 전략 간 선택의 근거가 되지 않는다.**

- **`DIRECT` 시나리오 ①의 1회차만 140.3ms로 튀었다.** 나머지 회차는 20ms대이며 다른 전략에는 이런 편차가 없다. JVM 워밍업이라면 다른 전략의 1회차에서도 나타나야 하는데 `PESSIMISTIC` 1회차는 29.1ms다. 3회 중 1회라 원인을 단정할 수 없어 관찰 사실로만 기록한다.

- **정합성 기준으로는 `DIRECT`를 제외한 5개 전략의 우열을 가릴 수 없다.** 재고 정합성(5장)과 중복·멱등성(7장) 모두 만족하므로, 최종 선택은 성능을 기준으로 판단해야 한다.

## 8. 최종 검증 — 재고 10,000 / 요청 20,000

최종 요구사항을 최종 적용 후보 전략으로 검증한다.

**대상 전략**: `KAFKA` (Redis 선점 + Kafka 비동기 DB 저장)

**선정 근거**: 실험 B에서 규모가 커질수록 API 접수 지연시간 격차가 벌어졌다(기본 3.1배 → 공통최대 4.8배). 선착순 쿠폰은 접수 응답 속도가 사용자 경험에 직결되므로 `KAFKA`를 최종 후보로 확정했다. 설계 문서 §8.3의 지정과도 일치한다.

> 쿠폰 매핑: couponId 38 (재고 10,000). 요청 20,000건에는 서로 다른 `userId`가 필요하며 테스트 사용자 20,000명으로 충족한다.

### 8.1 사전 확인

20,000 VU는 부하 발생기 자체가 병목이 될 수 있어 실행 전 다음을 확인했다.

- [x] 부하 발생기 메모리 여유 확인 — 실험 A·B 측정값으로 예측
- [x] 공통최대(2,000 VU) 실행 시 발생기 자원 사용률 기록
- [x] 분산 실행 필요 여부 판단 — **불필요**
- [x] `KAFKA_WAIT_TIMEOUT=900`, `MAX_DURATION=10m` 적용
- [x] 테스트 사용자 20,000명 존재 확인
- [x] `ulimit -n 100000` 및 커널 파라미터 적용

| 항목 | 값 |
|---|---|
| 부하 발생기 사양 | c5.xlarge (4 vCPU / 8 GiB, 총 7,676 MB) |
| 유휴 시 메모리 사용량 | 626 MB |
| **20,000 VU 실행 중 최대 사용량** | **5,017 MB** |

**메모리 예측이 정확했다.** 실험 B에서 2,000 VU 측정으로 산출한 VU당 0.217 MB가 20,000 VU 실측 0.220 MB와 거의 일치했다. 선형 외삽이 이 규모까지 유효함이 확인됐다.

k6 공식 문서의 VU당 1~5 MB 기준을 적용했다면 20 GB가 필요하다고 판단해 인스턴스를 상향했을 것이나, **실측 기반 예측이 정확해 불필요한 비용을 피할 수 있었다.** 이 스크립트처럼 요청 하나에 카운터 몇 개만 쓰는 경우 공식 안내값보다 훨씬 낮게 나온다.

> **`ulimit -n`이 실질적 전제 조건이다.** 기본값 1,024로는 20,000개 동시 연결에 필요한 파일 디스크립터가 부족하다. 셸 세션마다 적용해야 하며 k6를 실행할 바로 그 창에서 설정해야 한다. 커널 파라미터(`ip_local_port_range`)는 인스턴스 재시작 시 초기화되므로 함께 재적용한다.

### 8.8 관찰 내용

- **재고 정합성은 어떤 조건에서도 깨지지 않았다.** 요청의 42%가 응답을 받지 못하는 극한 상황에서도, 전부 응답한 상황에서도 발급은 정확히 10,000건이었다. Redis Lua Script의 원자적 선점과 Kafka Consumer의 멱등 처리가 최종 규모에서 유효함이 6회 반복으로 확인됐다.

- **병목은 재고 제어가 아니라 웹 계층이었다.** `max-connections` 기본값 8,192가 동시 20,000 연결에 크게 못 미쳤고, 이것이 타임아웃 8,447건의 주된 원인으로 보인다. 설정 세 줄 변경으로 타임아웃이 0이 됐다. **이 실험이 검증하려던 Redis·Kafka 계층과는 무관한 제약이다.**

- **튜닝 설정에서 회차별 편차가 크다.** 1회차 avg 8,843ms에서 3회차 1,622ms로 5배 차이가 난다. 앱을 재기동한 직후라 스레드 2,000개 생성과 JVM 워밍업 비용이 1회차에 몰린 것으로 보인다. 3회차(p95 2,517ms)만 3초 기준을 통과한다.

- **4.2의 워밍업 정책을 이 규모에는 그대로 적용하기 어렵다.** 실험 A·B에서는 워밍업 영향이 기본 단계에서만 +13.6%였고 중간 이상에서는 사라졌으나, 20,000 VU에서는 1회차 편차가 5배다. 최종 규모에서는 워밍업 실행을 분리하는 편이 타당하며, 이 문서의 튜닝 설정 평균값도 1회차 영향으로 실제보다 보수적으로 나온 값이다.

- **부하 발생기 용량 예측이 유효했다.** 2,000 VU 실측(VU당 0.217 MB)으로 20,000 VU를 예측했고 실측값 0.220 MB와 1.4% 차이로 맞았다. 인스턴스를 상향하지 않고 c5.xlarge로 완주했다.

## 9. 정합성 종합

총 112회 실행(실험 A 50 + 실험 B 20 + 중복·멱등성 36 + 최종 검증 6)의 정합성 판정을 종합한다.

| 전략 | 초과 발급 | 재고 정합성 | 1인 1매 | requestId 중복 | 최종 판정 |
|---|:---:|:---:|:---:|:---:|---|
| DIRECT | **X** | **X** | O | O | **부적합** (기준 전략) |
| PESSIMISTIC | O | O | O | O | 적합 |
| OPTIMISTIC | O | O | O | O | 적합 |
| CONDITIONAL | O | O | O | O | 적합 |
| REDIS | O | O | O | O | 적합 |
| KAFKA | O | O | O | O | 적합 |

**`DIRECT`를 제외한 5개 전략이 모든 항목을 만족했다.** 재고 정합성(5·6·8장)과 중복·멱등성(7장) 어느 쪽에서도 실패 사례가 없다.

이것이 최종 선정 논리의 출발점이다. **정합성으로는 5개 전략의 우열을 가릴 수 없으므로 선택 기준은 성능이 된다.**

### 9.1 정합성이 깨진 사례 — `DIRECT`

동시성 제어가 없는 기준 전략에서만 정합성이 깨졌다. 재고 규모와 무관하게 **차감의 약 90%가 유실**됐다.

| 단계 | 재고 | 요청 | 발급 | 초과 발급 | 실제 재고 차감 | 차감 유실률 |
|---|---:|---:|---:|---:|---:|---:|
| 스모크 | 10 | 20 | 20 | 10 | 2 | 90% |
| 기본 | 100 | 200 | 200 | 100 | 21 | 90% |
| 중간 | 500 | 1,000 | 1,000 | 500 | 100 | 90% |
| 공통최대 | 1,000 | 2,000 | 2,000 | 1,000 | 201 | 90% |

**요청이 전부 성공한다.** 재고 확인과 차감 사이에 다른 요청이 끼어들어 같은 재고 값을 읽고 같은 값을 쓰기 때문이다. 실서비스라면 재고 1,000장짜리 이벤트에서 2,000명이 쿠폰을 받고, 그중 1,000명이 사용 시점에 거절당한다.

**다만 중복 발급은 막았다.** 같은 사용자가 10회 동시 신청해도 1장만 발급됐다(7장). DB의 `UNIQUE (coupon_id, user_id)`와 `UNIQUE (request_id)` 제약이 최종 방어선으로 작동한 결과다. **애플리케이션 레벨 제어가 없어도 DB 제약은 유효하다는 점이 실증됐다.**

### 9.2 장애·보상 동작 — 미검증

| 항목 | 실험 B | 최종 검증 | 합계 |
|---|---:|---:|---:|
| Consumer 재시도 | 0 | 0 | **0** |
| 최종 실패 (보상 처리) | 0 | 0 | **0** |
| Kafka 발행 실패 | 0 | 0 | **0** |

> [!WARNING]
> **이 실험은 Kafka의 장애 복구 능력을 검증하지 않았다.**
>
> 26회 실행 전체에서 재시도·보상·발행 실패가 한 건도 발생하지 않았다. 정상 경로만 실행됐으므로 "장애가 나도 재고가 복구된다"는 결론을 이 실험에서 도출할 수 없다.

### 10.1 처리량 확장성

단계별 처리량 추이다(req/s).

| 전략 | 스모크 | 기본 | 중간 | 공통최대 | 중간→최대 |
|---|---:|---:|---:|---:|---:|
| DIRECT | 85.38 | 116.20 | 137.29 | 138.55 | +0.9% |
| PESSIMISTIC | 92.67 | 166.85 | 218.27 | 227.16 | +4.1% |
| OPTIMISTIC | 66.64 | 158.00 | 202.72 | 214.50 | +5.8% |
| CONDITIONAL | 100.98 | 177.71 | 225.65 | 234.64 | +4.0% |
| **REDIS** | 212.66 | 544.82 | 753.29 | 854.66 | **+13.5%** |

**DB 전략은 220~235 req/s에서 천장을 쳤다.** 요청을 두 배로 늘려도 처리량은 4~6%만 올랐고 응답시간만 두 배가 됐다(4,187ms → 8,005ms). 처리량이 포화되고 대기 시간만 증가하는 병목 패턴이다.

`REDIS`는 같은 구간에서 13.5% 상승했다. **이 규모에서 아직 포화점에 도달하지 않았다.**

### 10.2 반복 실행 편차

공통최대 3회 기준이다.

| 전략 | req/s 최소~최대 | 편차 | p95 최소~최대 | 평가 |
|---|---|---:|---|---|
| DIRECT | 136.54 ~ 141.28 | 3.5% | 12,832 ~ 13,122 | 안정 |
| PESSIMISTIC | 224.45 ~ 230.50 | 2.7% | 8,034 ~ 8,375 | 안정 |
| OPTIMISTIC | 210.71 ~ 216.92 | 2.9% | 8,689 ~ 9,006 | 안정 |
| CONDITIONAL | 233.62 ~ 236.10 | 1.1% | 7,987 ~ 8,035 | 안정 |
| REDIS (실험 A) | 793.45 ~ 934.88 | **17.8%** | 1,899 ~ 2,000 | 처리량 편차 큼 |
| REDIS (실험 B) | 870.98 ~ 895.47 | 2.8% | 1,736 ~ 1,855 | 안정 |
| KAFKA | 334.77 ~ 427.59 | **27.7%** | 430 ~ 549 | 처리량 편차 큼 |

**응답시간은 전 전략이 안정적이다.** 편차가 큰 것은 처리량 수치이며, `REDIS`·`KAFKA`처럼 실행이 빠른 전략일수록 전체 실행 시간이 짧아 측정 오차가 비율로 크게 나타난다. `KAFKA`는 Consumer 대기 시간까지 분모에 들어가 편차가 더 커진다.

**결론에 사용하는 값은 응답시간 기준이며, 처리량은 추세 확인용으로만 쓴다.**

### 10.3 워밍업 영향

| 규모 | 1회차 → 3회차 (`CONDITIONAL` req/s) | 변화 |
|---|---|---:|
| 기본 (200 요청) | 166.21 → 188.87 | +13.6% |
| 중간 (1,000 요청) | 225.28 → 224.48 | -0.4% |
| 공통최대 (2,000 요청) | 236.10 → 233.62 | -1.1% |
| **최종 검증 (20,000 요청, 튜닝)** | avg 8,843ms → 1,622ms | **5.4배** |

작은 규모와 최대 규모에서만 워밍업 영향이 크다. 중간 구간에서는 사라진다.

**최종 검증의 5.4배 편차는 앱 재기동 직후 스레드 2,000개 생성과 JVM 워밍업이 1회차에 몰린 결과다.** 4.2에서 "워밍업을 분리하지 않는다"고 정했으나, 이 규모에는 그대로 적용하기 어렵다. 8장의 튜닝 설정 평균값은 1회차 영향으로 실제보다 보수적인 값이다.

## 11. 전략별 분석

### 11.1 DIRECT

**측정에서 관찰된 현상**

- 모든 단계에서 요청 전부가 발급에 성공했다. 재고 1,000에 2,000건이 발급됐다.
- 재고 차감의 약 90%가 유실됐다. 규모와 무관하게 일정한 비율로 나타났다.
- 공통최대 138.55 req/s, p95 12,988ms로 **6개 전략 중 가장 느리다.** 정합성을 포기했는데도 성능이 최하위다.
- **중복 차단은 36회 전부 통과했다.** DB `UNIQUE` 제약이 최종 방어선으로 작동했다.

**장점**

- 구현이 가장 단순하다. 락도 재시도도 없다.
- 다른 전략의 개선 효과를 재는 기준선 역할을 한다.

**단점**

- **정합성을 전혀 보장하지 못한다.** 모든 단계에서 요청 전부가 발급에 성공했고 차감의 90%가 유실됐다.
- **정합성을 포기했음에도 가장 느리다.** 공통최대에서 138.55 req/s로 6개 전략 중 최저다.

### 11.2 PESSIMISTIC

**측정에서 관찰된 현상**

- 전 단계에서 정확히 재고만큼 발급했고 정합성을 지켰다.
- 공통최대 227.16 req/s, p95 8,195ms. DB 전략 중 두 번째로 빠르다.
- 반복 편차가 2.7%로 안정적이다.
- 중복 차단 평균 24.5ms로 DB 전략 중 가장 빠르다.

**장점**

- 정합성이 확실하고 동작을 예측하기 쉽다.
- 재시도 로직이 없어 구현과 디버깅이 단순하다.

**단점**

- 락 대기 동안 커넥션을 점유해 경합이 커질수록 확장이 막힌다.
- 중간 단계부터 p95 3초 기준을 넘겼다.
- Lock Timeout·Deadlock 재시도 정책이 없다.

### 11.3 OPTIMISTIC

**측정에서 관찰된 현상**

- 정합성은 전 단계에서 지켰다.
- 공통최대 214.50 req/s, p95 8,798ms로 **DB 전략 중 가장 느리다.**
- 중복 차단도 평균 44.1ms로 DB 전략 중 가장 느리다.

**장점**

- 명시적 락을 잡지 않아 락 대기가 없다.
- 경합이 낮은 상황에서는 유리할 수 있다.

**단점**

- **높은 경합에서 불리하다.** 버전 충돌이 잦아지면 재시도가 반복되고, 재시도마다 조회와 UPDATE를 다시 수행한다.
- 최대 재시도(10회) 소진 시 500 오류로 처리된다. 이번 측정에서는 발생하지 않았으나 더 높은 경합에서는 가능하다.
- 재시도 횟수를 측정하지 못했다. 느린 원인을 충돌 빈도로 확증하려면 별도 계측이 필요하다.

### 11.4 CONDITIONAL

**측정에서 관찰된 현상**

- 정합성을 지키면서 **DB 전략 중 가장 빠르다.** 공통최대 234.64 req/s, p95 8,005ms.
- 반복 편차 1.1%로 6개 전략 중 가장 안정적이다.
- 중복 차단 26.4ms로 `PESSIMISTIC`과 비슷하다.

**장점**

- 조회와 차감을 원자적 UPDATE 한 번으로 처리해 왕복이 적다.
- 재시도 로직이 없어 구현이 단순하면서 성능이 가장 좋다.
- **DB만으로 갈 경우 최선의 선택이다.**

**단점**

- 여전히 재고 한 행에 대한 직렬화를 벗어나지 못해 중간 단계부터 3초 기준을 넘긴다.
- UPDATE 0건이 쿠폰 미존재인지 매진인지 구분되지 않아 별도 조회가 필요하다.

### 11.5 REDIS

**측정에서 관찰된 현상**

- 정합성을 지키면서 **전 단계에서 `p95 < 3초` 기준을 만족한 두 전략 중 하나다.**
- 공통최대 854.66 req/s로 DB 최선(`CONDITIONAL` 234.64)의 **3.6배**다.
- 중간→최대 구간에서 처리량이 13.5% 상승해 아직 포화되지 않았다.
- 중복 차단 2.9ms로 DB 전략보다 **14배 빠르다.** Lua Script가 DB에 도달하기 전에 판정한다.

**장점**

- 재고 차감과 중복 검사를 Lua Script 한 번으로 원자적으로 처리한다.
- DB 부하를 재고 경합에서 분리한다.
- 응답 시점에 DB 저장까지 끝나므로 **접수와 완료가 일치한다.**

**단점**

- Redis와 DB 두 저장소의 정합성을 애플리케이션이 책임진다. DB 저장 실패 시 보상 로직이 필요하다.
- 중복 방지 키에 TTL이 없어 장기 운영 시 누적된다.
- 초기화에 `KEYS`를 사용해 운영 환경에서는 Blocking 위험이 있다.

### 11.6 KAFKA

**측정에서 관찰된 현상**

- 정합성을 전 단계에서 지켰고, 최종 검증(재고 10,000 / 요청 20,000)에서도 정확히 10,000건을 발급했다.
- 공통최대 접수 지연 avg 262.8ms로 `REDIS`(1,262.9ms)의 **4.8배 빠르다.** 규모가 커질수록 격차가 벌어졌다(2.4 → 3.1 → 4.3 → 4.8배).
- 최종 완료시간은 `REDIS` 2.28초 대비 5.22초로 **2.3배 느리다.**
- 26회 실행에서 Consumer 재시도·보상 0건.

**장점**

- **API 응답과 DB 저장을 분리한다.** 사용자는 DB 쓰기를 기다리지 않는다.
- 규모가 커질수록 접수 지연 우위가 커진다.
- Consumer가 실패해도 재시도·보상 경로가 준비돼 있다.

**단점**

- **최종 완료가 늦다.** 다만 이는 큐 구조 자체보다 Consumer 동시성 3 설정의 영향이 크다. 1,000건에 5.22초면 초당 190건으로, 파티션과 동시성을 올리면 좁혀질 여지가 있다.
- `WAITING` 응답 후 최종 결과를 조회할 API가 없다. 사용자에게 발급 완료를 알릴 수단이 없다.
- Consumer·재시도·보상·DLQ 등 운영 요소가 늘어난다. DLQ는 아직 구현되지 않았다.
- **장애 복구 능력이 실부하에서 검증되지 않았다** (9.2 참조).

## 12. 결론

### 12.1 실험 결과 해석

**정합성 — 변별력이 없다**

`DIRECT`를 제외한 5개 전략이 재고 정합성·1인 1매·중복 요청 차단을 모두 만족했다. 112회 실행에서 실패 사례가 없다.

**따라서 정합성은 선택 기준이 되지 못한다.** 이것이 이번 실험의 첫 번째 결론이며, 성능을 기준으로 선택해도 되는 근거다. 정합성을 검증하지 않았다면 "다른 전략도 정확한지 모르는 채 성능만 보고 골랐다"는 지적을 피할 수 없었다.

**성능 — 여기서 갈린다**

DB 전략 4개는 중간 단계(요청 1,000)부터 `p95 < 3초` 기준을 넘겼고, 공통최대에서 8~13초를 기록했다. 요청을 두 배로 늘려도 처리량은 4~6%만 상승해 **220~235 req/s에서 포화**했다.

`REDIS`는 공통최대에서 855 req/s, p95 1,941ms로 기준을 지켰고 아직 포화되지 않았다. DB 최선(`CONDITIONAL`) 대비 처리량 3.6배, 응답시간 4분의 1이다.

원인은 명확하다. **DB 전략은 재고 한 행을 두고 직렬화되지만, Redis는 메모리에서 원자 연산으로 처리한다.** 락 방식(비관적·낙관적·조건부)을 바꿔도 이 제약은 벗어나지 못했고, 세 전략이 11% 이내로 수렴했다.

**구현 복잡도 — 성능과 반대로 간다**

가장 빠른 전략이 가장 복잡하다.

```
DIRECT · CONDITIONAL   단순     정합성 실패 / 성능 한계
PESSIMISTIC            단순     성능 한계
OPTIMISTIC             중간     성능 한계 + 재시도 관리
REDIS                  중간     Redis-DB 두 저장소 정합성 책임
KAFKA                  높음     Consumer · 재시도 · 보상 · DLQ · 결과 조회 API
```

**운영 관점**

`REDIS`까지는 상태 저장소가 하나 늘어나는 수준이다. `KAFKA`는 성격이 다르다. Consumer 장애 대응, 재시도 정책, 보상 처리, DLQ, 그리고 **`WAITING` 응답 후 최종 결과를 알려줄 조회 API**가 모두 필요하다. 마지막 항목은 아직 구현되지 않았다.

또한 최종 검증에서 드러났듯 **웹 계층 설정이 별도의 병목**이다. Tomcat 기본값으로는 20,000 동시 요청 중 42%가 응답을 받지 못했다. 어떤 전략을 쓰든 이 계층의 튜닝이 선행되어야 한다.

### 12.2 핵심 질문에 대한 답

| 질문 | 답 |
|---|---|
| **DB 전략에서 어떤 병목이 발생했는가?** | 재고 한 행에 대한 직렬화다. 락 방식을 바꿔도(비관적·낙관적·조건부) 처리량이 220~235 req/s에 수렴했고 차이는 11% 이내였다. 요청을 1,000에서 2,000으로 늘려도 처리량은 4~6%만 오르고 응답시간만 두 배가 됐다(4,187ms → 8,005ms). 처리량 포화와 대기 증가가 동시에 나타나는 전형적 병목이다. |
| **Redis가 처리량과 정합성을 어떻게 개선했는가?** | 정합성은 개선한 것이 아니라 **DB 전략과 동일하게 유지**했다(112회 전부 통과). 개선된 것은 성능이다. 공통최대에서 855 req/s로 DB 최선의 3.6배, p95 1,941ms로 4분의 1이다. 중복 차단 비용도 2.9ms로 DB 전략(24~44ms)의 14분의 1이다. Lua Script가 재고 확인·중복 검사·차감을 원자적으로 처리해 DB 왕복 자체를 없앤 결과다. |
| **Kafka가 API 응답과 DB 처리를 얼마나 분리했는가?** | 접수 지연시간을 공통최대에서 1,262.9ms → 262.8ms로 **4.8배 단축**했다. 규모가 커질수록 격차가 벌어졌다(스모크 2.4배 → 공통최대 4.8배). 대신 모든 발급이 DB에 기록되는 최종 완료시간은 2.28초 → 5.22초로 **2.3배 늘어났다.** 다만 이 지연은 큐 구조 자체보다 Consumer 동시성 3 설정의 영향이 크다(초당 190건). |
| **추가된 운영 복잡도를 감수할 가치가 있는가?** | **이번 측정만으로는 단정할 수 없다.** `REDIS` 단독도 공통최대에서 p95 1,941ms로 3초 기준을 지켰으므로, 성능 요구사항이 Kafka를 강제하지 않는다. Kafka의 가치는 접수 응답 4.8배 개선이며, 이를 위해 Consumer·재시도·보상·DLQ·결과 조회 API를 감수할지는 **서비스 요구사항에 달린 판단**이다. 접수 응답 속도가 사용자 이탈에 직결되는 선착순 특성을 고려하면 정당화 가능하나, 측정값이 단독으로 결론을 내려주지는 않는다. |
| **장애 발생 후에도 재고와 발급 이력을 복구할 수 있는가?** | **이 실험은 답하지 못한다.** 실험 B·C 26회 전체에서 Consumer 재시도 0건, 보상 처리 0건, 발행 실패 0건으로 실패 경로를 한 번도 타지 않았다. 복구 동작은 자동화 테스트에서 FK 위반 시 Redis 재고 복구, 발행 Future 실패 시 재고·키 복구로 검증한 범위이며, **실부하 상황에서의 검증은 남아 있다.** |

### 12.3 최종 기술 선정

**선정 전략**: `REDIS_KAFKA` (Redis 재고 선점 + Kafka 비동기 DB 저장)

**선정 근거**

1. **정합성은 5개 전략이 동률이므로 성능이 기준이 된다.** 112회 실행에서 `DIRECT`를 제외한 전 전략이 재고 정합성·1인 1매·중복 차단을 만족했다.

2. **DB 전략은 요구 규모를 감당하지 못한다.** 중간 단계(요청 1,000)부터 `p95 < 3초` 기준을 넘겼고 220~235 req/s에서 포화했다. 락 방식을 바꿔 얻을 수 있는 개선은 11% 이내다. **최종 요구사항(요청 20,000)에 도달할 수 없다.**

3. **Redis는 필수다.** 정합성을 유지하면서 처리량 3.6배, 응답시간 4분의 1, 중복 차단 비용 14분의 1을 달성했다. 전 구간에서 3초 기준을 지킨 두 전략 중 하나다.

4. **Kafka는 접수 응답 속도를 위한 선택이다.** 접수 지연을 4.8배 단축하며, 규모가 커질수록 격차가 커진다. 선착순 쿠폰에서 "신청되었습니다"가 즉시 뜨는 것은 사용자 이탈과 직결된다.

5. **최종 요구사항을 실제로 충족했다.** 재고 10,000 / 요청 20,000에서 6회 모두 정확히 10,000건을 발급했고 초과 발급 0건, 정합성 통과다.

**감수하는 트레이드오프**

| 항목 | 내용 |
|---|---|
| 최종 완료 지연 | 접수 후 실제 DB 기록까지 최대 5.22초. Consumer 동시성 조정으로 개선 여지가 있다 |
| 결과 조회 필요 | `WAITING` 응답 이후 최종 성공·실패를 알릴 API가 필요하다. 미구현이다 |
| 운영 요소 증가 | Consumer 관리, 재시도 정책, 보상 처리, DLQ 구성이 추가된다 |
| 저장소 이중화 | Redis와 DB의 정합성을 애플리케이션이 책임진다 |
| 장애 복구 미검증 | 실부하에서 실패 경로를 확인하지 못했다 |

> [!IMPORTANT]
> **이 선정은 조건부다.**
>
> `REDIS` 단독도 공통최대(요청 2,000)에서 `p95 < 3초` 기준을 지켰고, **최종 규모(요청 20,000)에서 `REDIS` 단독과 직접 비교한 데이터는 없다.** 실험 C는 설계 문서 §8.3에 따라 `KAFKA`만 실행했다.
>
> 따라서 "Kafka 없이는 불가능하다"가 아니라 **"Kafka를 쓰면 접수 응답이 4.8배 빨라지며, 그 대가로 운영 복잡도와 완료 지연을 감수한다"** 가 정확한 표현이다.
>
> 운영 복잡도를 최소화하는 것이 더 중요한 상황이라면 `REDIS` 단독도 유효한 선택지다. 최종 시스템 설계 시 이 비교를 먼저 수행하는 것을 권한다.

**최종 시스템에서 우선 해결할 과제**

1. 발급 결과 조회 API (`GET /coupon-issues/requests/{requestId}`)
2. 웹 계층 설정 튜닝 — 기본값으로는 20,000 동시 요청의 42%가 응답을 받지 못했다
3. Kafka Consumer 동시성·파티션 수 조정으로 완료 지연 단축
4. Dead Letter Topic 구성과 관리자 재처리 절차
5. Redis 중복 방지 키 TTL 정책
6. 장애 주입 테스트로 복구 동작 실검증

이번 실험에서 확인하지 못했거나 결론이 가설에 머문 항목이다. 우선순위 순이다.
