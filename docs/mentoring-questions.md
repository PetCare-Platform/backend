# 프로젝트 멘토링 질문

1. 실험에서 Redis 단독도 요청 2,000까지 p95 2초 이내로 목표를 지켰고, Kafka를 붙이면 접수 응답이 4.8배 빨라지는 대신 최종 완료는 2.3배 느려졌습니다. 최종 검증(재고 10,000 / 요청 20,000)에서는 6회 모두 정합성을 통과했습니다. 저희는 접수 응답 속도를 우선해 Redis+Kafka를 선택했는데, 이 프로젝트 규모에서 이 선택이 타당한가요?

2. 저희는 API에서 Redis Lua로 재고를 선점한 뒤 Kafka에 발행하고 `WAITING`을 응답하며, Consumer가 DB에 발급 이력을 저장하는 구조로 구현했습니다. 이 구조는 재고 판정이 응답 시점에 끝나 사용자가 당첨·매진을 즉시 알 수 있지만, API가 Redis에 묶여 있어 Redis 장애 시 발급 전체가 멈춥니다. 반대로 요청 자체를 Kafka에 넣고 Consumer가 재고를 확보하는 구조는 API가 가볍고 트래픽 스파이크를 큐가 흡수하지만, 재고 판정이 늦어져 결과를 나중에 알려줘야 합니다. 선착순 쿠폰에서는 어느 쪽 트레이드오프를 택하는 것이 맞을까요? 그리고 저희처럼 Redis 선점 구조로 간다면 Redis 단일 장애점은 어떻게 대비하나요?

3. 저희는 Redis Lua로 재고를 차감한 뒤 Kafka 발행이 실패하면, Redis 재고를 다시 늘리고 중복 방지 키를 삭제하는 보상 방식으로 구현했습니다. 다만 보상 처리 자체가 실패하거나 그 사이 애플리케이션이 종료되면 재고가 줄어든 채로 남습니다. 부하 테스트 26회에서는 발행 실패가 한 번도 발생하지 않아 이 경로는 단위 테스트로만 검증한 상태입니다. 이 프로젝트에서 보상 방식만으로 충분한지, 아니면 발행할 메시지를 DB에 먼저 기록하는 Outbox Pattern까지 필요한지 궁금합니다. 보상 실패까지 대비하려면 무엇을 더 해야 하나요?

4. 남은 기간에 모든 장애 대응을 구현하기 어렵다면, 멱등성, Kafka 재시도, Redis 재고 보상, 정합성 검증·복구, 모니터링, 그리고 `WAITING` 응답 이후 최종 결과를 알려줄 조회 API 중 저희가 먼저 만들어야 할 것은 무엇인가요?

5. 저희는 Redis `INCR`로 생성한 순번을 선착순 기준으로 사용하고 있습니다. 사용자가 클릭한 시점과 요청이 서버에 도착한 시점은 네트워크 지연 때문에 순서가 뒤바뀔 수 있는데, 이 기준이 적절한가요? 그리고 발급이 취소되어 재고를 보상하면 이미 사용된 순번에 구멍이 생기는데 이것은 문제가 되지 않나요?

6. Redis 단독 방식은 DB 저장까지 마치고 응답하고, Redis+Kafka 방식은 요청 접수 후 `WAITING`으로 응답합니다. 처리 범위가 달라서 저희는 접수 지연시간과 최종 DB 저장 완료시간을 분리해 측정하고, Consumer 대기 시간이 섞이는 처리량은 비교에서 제외했습니다. 이 방식으로 두 전략을 공정하게 비교했다고 할 수 있나요?

7. 선착순 쿠폰 프로젝트는 대부분 Redis와 Kafka를 사용해 전체적인 기술 스택과 아키텍처가 비슷해지는 것 같습니다. 이런 상황에서 다른 팀과 차별점을 만들려면 어떤 부분을 더 깊게 구현하고 보여주는 것이 좋을까요?

8. 현재 프로젝트에는 실제 주문/결제 흐름이 포함되어 있지 않지만, coupon_issue.status 테이블에는 USED 상태가 존재합니다. 시연을 위해 쿠폰 사용 처리 API를 별도로 구현하여 상태 변경을 테스트하는 것이 좋을지, 아니면 이번 프로젝트 범위에서는 ISSUED 상태까지만 실동작을 구현하고, USED 상태 전이는 비즈니스 명세상의 확장 가능성으로 남겨두어도 충분한지 궁금합니다.

9. 트래픽 흡수를 위해 API 서버 앞단에 ALB나 Nginx를 배치하고,뒷단에는 Redis와 Kafka까지 두게 되면 시스템 전체 레이어가 길어져 정합성 유지와 장애 포인트나 관리 복잡도가 증가한다고 생각합니다. 실무에서 컴포넌트를 추가하여 얻는 안정성 이점이 이러한 리스크를 감수할 만큼 크다고 판단하는 기준이 무엇인지 궁금합니다.
